--- index 1
file: examples/cq_spurious_select_repro.zig lines 92-98
title: Every error return in driver() skips the close/cancelAll/drain teardown, leaving in-flight completions registered with the event loop while the coroutine frame and its fds are torn down (use-after-free).
The teardown at lines 129-132 runs only when the generation loop completes normally. On `return error.Spurious` (line 96), `return err` (line 98), or any failed `try cq.submit` (lines 79, 81, 104, 107, 117, 120), the still-pending NetRecv and Timer completions remain registered with the backend loop while the deferred closes run on their fds and the coroutine's stack frame -- holding `cq`, `recv_op`, `t1`, `recv_buf`, `iov` -- is released and recycled. A late completion then makes ownerCallback push into the freed CompletionQueue and the backend write into the freed buffer. This is not theoretical: the spurious-detection path the example exists to trigger exits through exactly this hole, and main joins the remaining workers (up to the full 20000 generations each) before calling exit(2), so the dangling operation has ample time to fire; a successful reproduction can therefore crash with unrelated memory corruption instead of the clean SPURIOUS line and exit 2 the doc comment promises. Fix: perform the close(); cancelAll(.keep); drain teardown in a defer (it is idempotent enough for the success path), or errdefer it, so no path leaves operations in flight.

--- index 2
file: examples/cq_spurious_select_repro.zig lines 48-49
title: flooder() races feed_fd against the driver's close: it can write to a closed fd or one already reused by another generation's socketpair.
Between `sh.feed_fd.load` and `std.c.write`, the driver (on another executor thread) can store -1, close fds[1], and start a new generation whose socketpair -- or another worker's -- reuses the same fd number. The flooder then writes its byte into an unrelated socket. In this program the effect is benign (a stray byte into some socketpair, or an ignored EBADF), but it is a genuine cross-thread TOCTOU in the changed code and makes the feeding nondeterministic. A fix is to give the flooder ownership of the write end for the generation (e.g. hand over the fd through the channel and have the flooder acknowledge before close), or simply tolerate and document the race explicitly.

--- index 3
file: examples/cq_spurious_select_repro.zig lines 172-185
title: Exit code 2 conflates infrastructure failures with a reproduction, contradicting the documented exit contract, and the join catch discards the actual error.
The doc comment (lines 27-30) defines exit 2 as 'the repro detects the spurious win itself' and exit 0 as no reproduction. But `failed` is set by any driver error -- error.SocketPair from fd exhaustion, a submit error -- and also produces exit 2, so a harness keying on the exit code misreads an environment failure as a reproduction (only the RESULT spurious=0 line disambiguates). The `catch { failed = true; }` also throws away which error occurred, losing the diagnosis. Fix: capture the join error, print it, and use a distinct exit code (or propagate the error) for non-Spurious failures, reserving exit 2 for spurious > 0.
