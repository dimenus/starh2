## Analysis

**The repro's teardown closes the descriptors while still holding the mutex — the exact version the commit message says deadlocks.** The commit message is explicit: "the driver clears the descriptor under the mutex BEFORE closing it after unlock" and "The close must stay OUTSIDE the mutex. A first version closed under the hold and deadlocked about one run in ten on macOS." But the landed defer is:

```85:91:tools/review-recall/corpus/0c9271ce/tree/examples/cq_spurious_select_repro.zig
        defer {
            sh.feed_mu.lockUncancelable();
            defer sh.feed_mu.unlock();
            sh.feed_fd = -1;
            _ = std.c.close(fds[0]);
            _ = std.c.close(fds[1]);
        }
```

The inner `defer sh.feed_mu.unlock()` runs when the outer defer block exits — after both `close` calls. So the closes happen under the mutex hold, and the in-file comment ("Clear and close under one mutex hold") documents the deadlock-prone version as intended. This is the first version the message describes: `close` can block in the kernel on the executor thread running the driver, the flooder parks on `feed_mu` forever, and the other executor sleeps in kevent. It also means the message's verification claims (30 clean Debug runs on macOS) cannot have been made against this code. The fix is to set `feed_fd = -1` under the mutex, unlock, then close.

**A new descriptor leak on the cancellation path.** The old code declared `defer close(fds[0/1])` immediately after `fcntl`, before any fallible statement. The new code creates the socketpair (line 69), then does `try sh.feed_mu.lock()` at line 78, and only declares the close defer at line 85. If that cancelable lock returns `error.Canceled`, the driver returns with both fds leaked. Minor (example code, cancel path only), fixed by using `lockUncancelable` there too or declaring the close defer before locking.

**The rest checks out.** `zio.Mutex` really has `.init`, a cancelable `lock`, and `lockUncancelable`, so the API use is valid, and `lockUncancelable` is the right choice inside a defer. Defer ordering is correct: the errdefer/explicit queue teardown drains the ops referencing the fds before the close defer runs. The `build.zig` `posix_only` gate behaves as described (silent skip on full Windows builds, `addFail` on direct selection), and nothing in-tree consumes `cq_two_driver_misuse`'s exit code, so the 0 → 3 change is self-consistent with its rewritten header (abort = expected, 3 = check failed, error-from-main = exit 1).
