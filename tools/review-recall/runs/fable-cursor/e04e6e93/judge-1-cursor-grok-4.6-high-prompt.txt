title: updateNow's new 'owner-thread only' claim is false: cross-thread setTimer writes tick/now under the timer lock while poll's two updateNow calls write them unlocked, an unsynchronized data race.
The comment justifies dropping the timer lock by saying only the cross-thread clearTimer exists and it never reads now/tick. But setTimer is also used cross-thread: the tree's test "clearTimer racing a firing timer (cross-thread)" calls loop.setTimer from a non-owner thread and its comment lists it among "the thread-safe setTimer/clearTimer/wake APIs", and the timer_mutex doc (lines 269-272) states the lock protects "the cached `now` values", which is only meaningful for cross-thread access. setTimer -> updateNow (line 636) and armTimer -> nowFor mutate tick, now[], and now_tick[] under the lock, while poll mutates the same plain u64 fields with no lock at lines 1392 and 1429 (tick +%= 1 is a read-modify-write), and Loop.now() reads now[0] unlocked. Concurrent unsynchronized access to non-atomic fields is a data race (torn reads on 32-bit, lost tick bumps, TSan failure); a cross-thread setTimer can compute a .duration deadline from a torn or stale snapshot. The pre-poll updateNow added by this push widens the window, and the new comment plus the contradicted timer_mutex doc enshrine a false invariant. Fix: pick one contract - either make setTimer owner-thread-only (assertOwnThread, delete the cross-thread test path) and update the timer_mutex doc to drop "and the cached `now` values", or keep poll's snapshot writes under the timer lock / make tick and now[0] atomic.
