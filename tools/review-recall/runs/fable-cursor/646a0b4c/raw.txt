I've finished the review. Here is my assessment of the push, followed by the findings block.

**What the push does.** It adds one public predicate, `CompletionQueue.isDrained()` (closed AND pending empty AND completed empty, under the mutex), and rewrites the `getResult` comment to direct a select driver that received `error.Closed` to disambiguate with it: `false` means keep driving, `true` means the terminal state.

**The mechanism is sound.** I traced the races the commit message claims are benign and agree. The terminal state is sticky: `closed` never clears, a closed queue refuses `submit`, and `ownerCallback` moves a node from `pending` to `completed` under one mutex hold, so `closed && pending empty && completed empty` cannot regress once observed. Every non-terminal `false` answer has a guaranteed future wake: an in-flight operation wakes through `ownerCallback` (`close` over in-flight stays silent by design, line 159–165), and a drained `close` bumps the signal itself. A completion landing between the failed pop in `getResult` and the `isDrained` check only turns a would-be `true` into `false`, which is the safe direction. `asyncWait`'s post-registration `isReady` double-check closes the park-forever window on the re-poll.

**What I would raise.** Three things, all in the touched file:

1. `isDrained` ships with no test at all, including the cheap deterministic states: open empty queue → `false`, closed with an operation in flight → `false` (the exact case the commit says doomed `isClosed`), closed and drained → `true`. Two existing tests ("select on a drained queue…", "close over an in-flight operation…") already construct these states and could pin the predicate in a line each.

2. The module header still claims the select win "is what `wait` would have returned, with one difference" (cancel semantics). This push cements a second difference — the select arm can report `error.Closed` spuriously on an open or undrained queue, which `wait` never does — and a consumer following the header writes exactly the leaking driver the commit message describes. The contract lives only in the `getResult` internals and the new doc comment; the primary doc surface contradicts it.

3. The `signal` field doc still says "The future protocol depends on the strict reading of a wake: a completion is takeable, or the queue is drained." The change explicitly abandons that dependency (stale wakes are now an accepted input the caller disambiguates), so the field doc asserts an invariant the code no longer relies on or upholds.
