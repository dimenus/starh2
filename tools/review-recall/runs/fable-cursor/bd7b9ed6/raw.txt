I've read the whole touched file and confirmed how the queue's future protocol and consumers sit. Here's my assessment of this push.

The commit adds one public method, `isClosed()`, so a select driver can distinguish a spurious `error.Closed` (stale wake on an open queue, documented at `getResult`) from a real close. The mutex use is correct (`closed` is written under `mutex`), and exposing a predicate rather than changing the `Closeable!*Completion` contract is a reasonable shape.

The substantive problem is that the disambiguation protocol itself has a hole. The doc comment and commit message claim the check works "whoever closes the queue", but `isClosed()` is not atomic with the `getResult` call that produced the `error.Closed`. If a stale wake wins the queue arm while operations are in flight, and another task then calls `close()` before the driver checks, the driver sees `error.Closed` with `isClosed() == true` and stops draining — yet the queue is closed but not drained. `close()`'s own contract says in-flight operations "keep running and are still delivered", and the module header requires the driver to drain and free heap-backed submissions, so stopping here abandons or leaks them. The race-free predicate is drained-ness (`closed and pending.isEmpty() and completed.isEmpty()`), which is a latched, monotonic state on a closed queue: false always means "re-poll safely", true genuinely means nothing more will ever arrive. `isClosed()` alone is the wrong half of that condition.

Two smaller points: the new public API lands with no test at all (not even close-then-check, let alone the select-driver re-poll it exists for), and the module header (lines 52–57) still says a select win "is what `wait` would have returned, with one difference" — the spurious `error.Closed` is a second difference, and the header never points a select driver at the re-poll protocol this commit is building.
