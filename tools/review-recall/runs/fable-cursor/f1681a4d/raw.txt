## Review

**The change.** `Loop.poll` now calls `state.updateNow()` right after a backend poll that could have waited, so `.duration` timers armed between polls (the runtime's task batch) are no longer backdated by the sleep. A regression test reproduces the exact wake shape (I/O completion delivered by the sleeping poll, timer armed after `poll` returns).

The fix is correct for the shape it targets, and the test is well-constructed: libc is linked for the test module (`build.zig` line 41), `posix.pipe`/`fs.close`/`os/time` APIs all exist as used, the Windows skip is justified (the forced `pollable = true` readiness path is unsupported there), and the timing tolerances (450–1500 ms) have sane slack. Two problems survive scrutiny:

**1. The refresh runs after inline completion callbacks have already executed, so the new comment overclaims and the bug class remains reachable.** Backends invoke non-deferred completion callbacks *inside* `backend.poll` (`markCompletedFromBackend` → `markCompleted` → `dispatchCompletion` → `finishCompletion` → `completion.call`; only `defer_callback`/`rearm`/null-callback completions are queued for later). The new comment says the refresh covers "completion callbacks here", but those callbacks ran at line 1426, before the refresh at line 1437. A raw-loop consumer arming a `.duration` timer via `loop.add` from an I/O completion callback — e.g. arming a read timeout when a connection becomes readable, precisely the HTTP/2 shape from the commit message, one level down — still computes its deadline from the pre-sleep snapshot and fires immediately. The zio runtime itself is safe (task wakes travel through `dispatched` and run after `poll` returns), which is why the regression test passes, but the test covers only the task-batch shape. Fix: refresh before completions are delivered (inside the backends, after the wait syscall) or take the commit's rejected alternative of a fresh read per `.duration` arm.

**2. The new `updateNow()` mutates `tick`/`now` without the timer mutex, racing cross-thread `setTimer`.** `setTimer` calls `updateNow` under `timer_mutex` (loop.zig lines 621–634), and the tree's own test "clearTimer racing a firing timer (cross-thread)" drives `setTimer` from a non-owner thread, calling it a thread-safe API. The new call site writes `tick`, `now[0]` and `now_tick[0]` with no lock, concurrently with that locked writer — an unsynchronized read-modify-write on plain `u64`s (a data race TSan would flag; a torn `tick` can mis-cache boot/real `now` for a scan). The same flaw pre-exists in `checkTimers`' unlocked `updateNow` (line 982), whose justifying comment — "`updateNow` is called here and in `setTimer`, both owner-thread" — both contradicts the cross-thread test and is now also stale, since this change adds a third call site it doesn't mention. Either the new call takes `lockTimers()` (matching `setTimer`) or the owner-thread-only contract needs to be made real and the comments/test reconciled.

Not reported, deliberately: the redundant second `updateNow` inside `checkTimers` on timed-out polls costs one extra clock read and is defensible (thread-pool completions can arrive on a timed-out poll); the 1.2 s test sleep is a fair price for the regression shape; the unchecked `std.c.write` cannot realistically fail for one byte on an empty pipe with no signals in flight.
