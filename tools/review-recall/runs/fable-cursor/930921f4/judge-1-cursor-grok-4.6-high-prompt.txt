title: Spurious error.Closed on an open queue is indistinguishable from a real close for callers whose queue can be closed by another task, silently tearing down the documented dispatcher pattern.
getResult now returns error.Closed for a spurious select win with the queue EMPTY and OPEN. The comment's escape hatch — 'a caller that knows it never closed its own queue' — does not cover the library's own headline scenario: close() is thread-safe and the module header's long-lived dispatcher exists precisely so other tasks can submit (and close). For such a driver a spurious Closed and a genuine drained close are byte-identical, and the documented pattern 'error.Closed => break' exits the drive loop on an open queue with operations in flight; heap-backed operations owned by the driver (header lines 14-20) are then never drained or freed. The old assert crashed loudly at the protocol bug; this returns a well-typed lie. The Result type Closeable!*Completion cannot express 'spurious, re-poll', so the fix is either the acknowledged upstream signal-accounting repair before shipping this, or a contract change (e.g. a distinct retryable error / getResult re-checking closed-and-drained under the mutex it already holds so a genuine close stays unambiguous and the spurious case is at least observable).
