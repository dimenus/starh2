title: Partial worker startup failure can leave running tasks using freed memory.
In `go`, task handles and shared state arrays are allocated, then flooder/driver tasks are spawned in a loop with `try`. If any later `spawn` fails, the function unwinds immediately and the deferred `alloc.free(...)` calls run, but already spawned tasks keep running and still dereference `shs`, `chans`, and `bufs`. This creates a use-after-free race/crash path on spawn error (e.g. allocation/resource exhaustion). Track how many tasks were started and join/cancel them before freeing shared allocations, or use a `zio.Group` that guarantees teardown on failure.
