This push stops `getResult` from asserting that a select win is a takeable completion or a drained queue. `wait()` still loops until that predicate is true; the select path now returns `error.Closed` whenever the pop is empty, including when the queue is open with work in flight.

That overloads the only error the `Closeable!*Completion` contract can name. The module header still says a select win is what `wait()` would have returned, the dispatcher example still `break`s on `Closed`, and `signal`’s comment still requires a strict reading of a wake. A driver that follows those docs will tear down a live queue. The new “re-poll if you never closed” rule lives only in the function body, and it is incomplete: `getResult` no longer looks at `closed` or `pending`, so a close that races with in-flight ops is indistinguishable from a genuine drain. `isReady` still implements the old predicate.

There is no test that `getResult` on an open empty queue returns `Closed`, nor that a select driver must continue after that result. The existing select test only covers a queue that was actually closed.
