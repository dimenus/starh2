title: Do not report an open queue as error.Closed.
After a stale wake, select returns error.Closed for a queue that is still open. error.Closed is overloaded, so a caller cannot tell a real close from a spurious win, and a multi-closer caller cannot disambiguate at all.

file: src/completion_queue.zig lines 302-320
title: getResult reports error.Closed for a still-open queue, but the public contract still treats Closed as drained.
After this change, getResult pops completed and, on an empty pop, always returns error.Closed. It no longer snapshots closed or pending, so Closed is now also the result for empty+open and for closed-with-in-flight. wait() and timedWait() still return Closed only when node == null && closed && pending.isEmpty(); isReady still uses that same predicate. The module header (lines 52–57) still says a select win is what wait() would have returned; the dispatcher example (lines 38–49) still breaks on Closed as “closed and fully drained”; the signal field (lines 80–86) still says the future protocol depends on a wake meaning a takeable completion or a drained queue; the future-protocol comment (lines 278–285) still says getResult reports Closed for drain. A select driver that follows that contract will tear down a live queue — the failure this commit measured — just without a ReleaseSafe crash. The body comment tells a caller that never closed the queue to re-poll; that rule is not in the public docs, is a second difference from wait() (which loops rather than returning), and is wrong when the caller did close but operations are still pending, because closed is no longer consulted. Either restore the drained check and change Result so the spurious case is not named Closed, or rewrite the public contract, the example, and the signal/future comments so a select driver must re-poll unless the queue is actually drained (isEmpty after close, not merely “I called close”).
