--- index 0
file: src/completion_queue.zig lines 381-390
title: isClosed does not distinguish a real drained close from a spurious Closed while work is still in flight.
The comment tells a select driver that `error.Closed` plus `isClosed() == false` is the only spurious case, so the implied other branch is to stop draining when `isClosed()` is true. That is not the stop condition `wait()` uses (`closed && pending.empty && completed.empty`), and it is not what `getResult` observed. `getResult` returns `error.Closed` whenever `completed` is empty, including on a stale select win. `close()` deliberately does not wake while operations are still pending, but a leftover select signal can still claim the arm then: `getResult` returns `error.Closed`, `isClosed()` is true, and a driver that stops as documented abandons in-flight (including heap-backed) operations. The same mis-stop happens if another task `submit`s and then `close`s between `getResult` and `isClosed` — two separate lock acquisitions, and both `submit` and `close` are documented thread-safe. The false direction is unambiguous because `closed` is sticky; the true direction is not. Stop only when the queue is closed and empty (`isClosed() && isEmpty()`, matching `wait`), and say that in the comment. Sampling `closed` and both queues under the same lock as the `getResult` pop would make the snapshot honest; `isClosed()` alone cannot.
