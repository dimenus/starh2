The new pre-poll updateNow exists so checkTimers decides the wait from a fresh clock, and so a deadline that passed during the previous task batch fires even when the backend poll is skipped. That skip is the executor's busy path: poll(.zero) with no backend inflight sets timed_out=false, so the post-timeout checkTimers never runs and only the pre-poll scan can fire. file: src/ev/loop.zig lines 383-391
title: updateNow writes now/tick without the timer lock while setTimer does so from other threads.
The new comment says updateNow is owner-thread only because cross-thread clearTimer never reads now/tick. That is incomplete: setTimer also calls updateNow, while holding timer_mutex, and the cross-thread timer test treats setTimer as a thread-safe API used from a non-owner thread while the owner is in poll. poll now calls updateNow twice with no lock (before checkTimers and after backend.poll), so those writes race with setTimer's locked writes of the same non-atomic tick, now[0], and now_tick[0]. timer_mutex's own comment still claims it protects the cached now values. Take the timer lock inside updateNow, or stop calling updateNow from setTimer and document setTimer as owner-thread only (and change the test).
